# GitLab Generator Implementation

This document details the GitLab generator implementation of the formal model defined in the paper. It outlines the mapping strategies, artifact handling, and specific constraints associated with the GitLab CI/CD platform.

The GitLab CI/CD generator will NOT support paid plans features.

## Gitlab Instruction

This section contains instructions for using the GitLab CI/CD generator.

### Connecting repository

To use pipelines from different version control, the project must be imported for CI/CD in GitLab.

Repositories must allow dependent component's pipeline tokens for the chaining to work.
Chaining will not work for repositories that are not generated by the generator, as it uses specific rules.

### Runner tags
The runner tags are defined in environment file for GitLab passed by in argument `--platform-env-file`, see [GitLabEnvironment.kt](../src/main/kotlin/generator/platforms/gitlab/GitLabEnvironment.kt)
Only one set (list) of tags for normal build and one set of tags for docker-in-docker is supported - The generator doesn't support choosing specific tags for specific build configurations

### Docker
It is advised against using DinD for security reasons.
The generator shall not support multi docker build configurations, as they require docker in docker and come with a security risk.
The generator provides a way to setup dind connection.

#### Docker registry connection

GitLab doesn't support fine-grained control over Docker registry connections.
Instead, each component can set up the Variable `DOCKER_AUTH_CONFIG` to the content of Docker's config.json file with connections.
Each build configuration has access to all registries defined

## Implementation Details

### 1. High‑level Mapping (Formal Model → GitLab)
- **Build Configuration**: Maps to a single GitLab job in the `default` stage when no matrix is defined. The dependency strict partial order is enforced using `needs`.
- **Build Matrix**: Maps to two jobs in the same pipeline:
    1. `<build-configuration-name>:run`: The execution job configured with `parallel: matrix`.
    2. `<build-configuration-name>`: An aggregation job that depends on `<build-configuration-name>:run`. It collects artifacts from all matrix shards and merges them into a unified artifact set for downstream consumers.
- **Stages**: The generator utilizes a single stage named `default`. Execution order is strictly controlled via the dependencies using `needs` keyword, ignoring standard stage ordering.
- **Build Steps**: Executed sequentially within the job's `script` section. `before_script` and `after_script` is utilised for environment setup (parameter exporting, artifact staging).

### 2. Workspace and Containers
- **Workspace**: All build steps for a configuration execute in the root of the workspace (`$CI_PROJECT_DIR`), adhering to the formal model's single directory concept. They can define workdir, which is then nested into `$CI_PROJECT_DIR`.
- **Images**: The Docker image is defined on the job level. If `Docker-in-Docker` (DinD) is required, the `docker:dind` service is attached, and appropriate tags/variables are configured based on the environment helper.

### 3. Artifact Handling
- **Publish Artifacts**: Artifacts are staged under a namespaced directory `_artifacts/<BC_NAME_SANITIZED>/` to prevent collisions. The job publishes artifacts `_artifacts/<BC_NAME_SANITIZED>/**`.
    - **Structure**: Consumers view the `_artifacts/...` directory structure. This namespacing facilitates clean-up and separation of concerns.
- **Dependency Artifacts**:
    - **Downloading**: The consumer job declares `needs: [{job: <UpstreamBC>, artifacts: true}]`. GitLab automatically downloads the upstream `_artifacts/` directory into the consumer's workspace.
    - **Extraction/Copying**: A generated `before_script` iterates through the declared dependencies. It copies files from `_artifacts/<UpstreamBC>/<Source>` to the local destination path.
    - **Archives**: The implementation supports extracting specific paths from archives (`.zip`, `.tar`, `.tar.gz`, `.tgz`) using syntax `package!path`. Logic is injected into the shell script to handle extraction tools (`unzip`, `tar`).

### 4. Parameter Management
- **Mechanism**: Parameters are exchanged via `dotenv` reports.
- **Export**: Producer jobs write parameters to a `build.env` file in the format `KEY=VALUE`. This file is published as a `dotenv` report artifact.
- **Import**: Consumer jobs automatically receive these variables in their environment via `needs`.
- **Naming**: Parameters are prefixed with the build configuration name (e.g., `BuildConf_ParamName`) to avoid collisions.
- **Shell Aliasing**: To support script execution, the `before_script` aliases these prefixed environment variables back to their local names (e.g., `export ParamName=$BuildConf_ParamName`).
  - This is the mechanism shortage and should be addressed in the future.

### 5. Triggers and Rules
- **VCS Triggers**: Mapped to GitLab `rules`.
    - **Wildcards**: Triggers matching `*` generate simple existence checks (e.g., `if: $CI_COMMIT_BRANCH`).
    - **Excludes**: Implemented as high-priority `when: never` rules.
    - **Changes**: `includePaths` are mapped to `changes` in GitLab rules.
- **Schedule Triggers**: GitLab requires schedules to be defined in the UI. The generator emits a rule allowing execution when `$CI_PIPELINE_SOURCE == 'schedule'` and logs the required cron/variables to the console output for manual setup.
- **Dependency triggering**: All build configurations in the dependency chain of `X`:
  - **Internal**: set `rules += X.rules` 
  - **External**: set rule: `STARTED_BY == X.name` to allow triggering by external pipelines.
  - And build configuration `X` creates a trigger job for dependency components. This trigger sets:
    - `rules = X.rules`
    - `STARTED_BY=X.name`
    - and triggers dependency component pipeline, waits for completion, and downloads artifacts.

### 6. External Upstream Dependencies
The formal model allows dependencies on external components. GitLab does not natively support "waiting" for an upstream pipeline in a different project easily within a single DAG view.

- **Implementation**: A specialized trigger job is generated for each external component dependency.
- **Mechanism**:
    1. The job uses `curl` to invoke the GitLab API (`/projects/:id/trigger/pipeline`) on the target external repository.
    2. It actively polls the status of the triggered pipeline until completion.
    3. Upon success, it downloads artifacts from the external jobs using the API.
- **Authentication**: Relies on `CI_JOB_TOKEN` or provided credentials.

## WorkInProgress

### 1. Per-step Containers
The current implementation sets the image at the job level. Support for distinct images per build step (via `docker run` inside the job) is referenced in legacy notes but needs verification in the current `BuildStepsRenderer`.

### 2. Parameter Optimization
Currently, all parameters are exported to `dotenv`. Future work involves analyzing the dependency graph to export only parameters explicitly required by downstream consumers.

### 3. Artifact Cleanup
While namespacing exists (`_artifacts/`), explicit logic to delete undeclared artifacts from the workspace after copying is implied but relies on the clean nature of the GitLab runner environment or subsequent script steps.
